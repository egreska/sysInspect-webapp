# Session secrets travel in iCloud Keychain

The password verifier and the Security Answer travel with the Session so a second phone on the same Inspector can log in and reset. They used to sit on the synced User record, which is the inspection store, so Backup Data and CloudKit carried the hashes. They now travel in iCloud Keychain, keyed by the Session's user id. After a phone copies them there, it clears passwordHash, passwordSalt, securityQuestion, securityAnswerHash, and securityAnswerSalt on User.

**Considered options:** Leave them on User. Keep them only on the phone that set them.

**Consequences:** The Security Answer stays the reset factor. Its question, answer hash, and salt travel in the same Keychain item as the password verifier. iCloud Keychain has to be on, and the item has to have arrived, before the second phone can check the password or the Security Answer. Until then, login and password reset stop and say this iPad does not have the password yet. That wait is not a wrong password, it does not count toward the email lock, and the app does not offer to set a new password. Every phone on that Apple ID moves to this build before anyone opens it, because an older build can write the columns again. The five attributes stay on the model so existing stores still open. CloudKit keeps prior record versions; clearing the current record is as far as the app can go. One Session per Apple ID stays the boundary. This supersedes the storage in ADR 0019 and keeps that decision's rule that a second phone must be able to reset once the Session's secrets have arrived.
